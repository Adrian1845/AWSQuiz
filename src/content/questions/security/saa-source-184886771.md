## Explanation

Correct option:

Use AWS Directory Service AD Connector to connect AWS to the on-premises Active Directory. Integrate AD Connector with AWS IAM Identity Center. Use permission sets to assign access to AWS accounts and resources based on Active Directory group membership

This solution provides a centralized, low-maintenance, and scalable identity management solution that integrates seamlessly with the company’s existing on-premises Active Directory. AD Connector acts as a proxy to the on-prem AD, eliminating the need to deploy or manage a separate directory in the cloud. By integrating IAM Identity Center (formerly AWS SSO) with AD Connector, the company can use existing Active Directory group memberships to assign permission sets that define what AWS accounts and resources each user can access. This allows fine-grained, role-based access control across multiple accounts managed by AWS Organizations. IAM Identity Center also provides a single sign-on portal, reducing friction for users while maintaining compliance and security. The entire solution requires minimal operational overhead and scales well with growing teams and AWS accounts.

Incorrect options:

Deploy AWS Directory Service for Microsoft Active Directory in AWS. Establish a trust relationship with the on-premises Active Directory. Use IAM roles linked to AD groups to control access to AWS resources - While this solution provides centralized identity integration via trust relationships, managing a self-hosted or AWS-managed AD in the cloud adds significant operational overhead. You must maintain the AWS Directory Service instance, monitor trust health, and manage role mappings manually. It does meet the technical need, but it’s less efficient than a fully managed identity federation service such as IAM Identity Center (formerly AWS SSO). It introduces extra cost and maintenance that goes against the requirement for low operational effort.

Deploy an open-source identity provider (IdP) on Amazon EC2. Synchronize it with the on-premises Active Directory and use SAML to federate access to AWS accounts. Assign IAM roles to federated users based on SAML assertions - While this solution is technically feasible, it introduces significant operational overhead, which contradicts the question’s requirement. Managing an open-source IdP on EC2 - including scaling, patching, high availability, and synchronization with Active Directory is labor-intensive. Although it allows for SAML federation and AWS access, it lacks the native integration, multi-account visibility, and permission set management offered by IAM Identity Center. This approach may suit specific customization needs but fails the test of being simple and low maintenance.

Use AWS Control Tower to enable account access for developers. Create AWS IAM roles in each member account and manually assign permissions. Instruct developers to assume roles across accounts using the AWS CLI - Although AWS Control Tower helps set up a multi-account environment, this approach involves manual creation and assignment of IAM roles in each account, which is not scalable. Developers must use CLI-based role assumption, and administrators must maintain custom trust policies and permission boundaries. There's no centralized management of access or visibility across accounts, making this solution error-prone and operationally complex compared to using IAM Identity Center with group-based permission sets and automatic propagation across accounts.
