## Matiz sobre la respuesta del examen (2026-10-26)

La clave de origen elige **A (SQS FIFO)**: entre las opciones ofrecidas, es la cola que deduplica envíos dentro de una ventana de cinco minutos. Sin embargo, la afirmación de que *cada solicitud se procesa exactamente una vez* es demasiado fuerte si se refiere al efecto final del trámite. Si el consumidor guarda el trámite y falla antes de borrar el mensaje, este puede volver a entregarse incluso con FIFO. También puede entrar un duplicado si el productor reintenta el envío después de la ventana de deduplicación. La aplicación debe usar un identificador estable de solicitud y hacer idempotente la escritura del backend. Una cola Standard con esa idempotencia también podría evitar efectos duplicados si no se necesita orden, pero esa implementación no aparece descrita en la opción B. [Deduplicación FIFO](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html) · [Reintentos y ventana de visibilidad](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/designing-for-outage-recovery-scenarios.html).

## Explanation

Correct option:

Implement an Amazon SQS FIFO queue to reliably buffer and deliver form submissions from the web application layer to the processing tier

SQS FIFO queues preserve order within a message group and deduplicate producer retries within a five-minute window. Of the listed queue choices, FIFO is the expected exam answer when duplicate submissions must be avoided. FIFO alone does not guarantee that the business operation runs exactly once: if processing finishes but the message is not deleted before the visibility timeout expires, a consumer may process it again. The application still needs an idempotent backend operation.

Incorrect options:

Implement an Amazon SQS standard queue to reliably buffer and deliver form submissions from the web application layer to the processing tier - Standard queues deliver at least once and provide best-effort ordering. The option does not specify application-level deduplication or idempotency, so it does not meet the stated requirement by itself. A Standard queue plus an idempotent consumer could avoid duplicate business effects if ordering is unnecessary; the question does not explicitly require ordering.

Leverage Amazon EventBridge to send events from the web application to the processing tier for asynchronous form handling - Amazon EventBridge is a powerful event bus that enables loosely coupled architectures and event-driven applications. However, it does not guarantee exactly-once delivery. Instead, EventBridge provides at-least-once delivery semantics, which means events can be delivered more than once in certain failure scenarios. So, the key shortcomings for this use case are - no built-in ordering of events and possible duplicate event delivery.

Leverage Amazon API Gateway to pass the form submissions to AWS Lambda for processing in real time - While API Gateway with Lambda is effective for real-time synchronous processing, it does not inherently offer decoupling between tiers or a durable queue. It also lacks native support for guaranteed exactly-once processing across asynchronous workloads.
